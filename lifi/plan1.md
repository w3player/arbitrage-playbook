# Plan 1：多链预置库存套利回测方案

> 对应模型：[多链预置库存套利](./01-prefunded-cross-chain-inventory.md)  
> 本文只设计回测与模拟交易，不发送真实交易，不执行跨链，不使用真实资金。

## 先给结论

这套回测不能只下载一份 K 线，然后比较两条链的价格。我们真正要验证的是：

1. 同一时间、同一数量的 WETH，在不同链是否存在可成交的价差；
2. 使用 LI.FI 的最低到账量、网络手续费和其他费用后，是否仍能赚钱；
3. 买入和卖出只有一笔成功时，最多会亏多少；
4. 多次交易后，某条链的 WETH 或 USDC 是否会被用完；
5. 补库存的费用、等待时间和失败，是否会吞掉套利收益；
6. 把全部闲置库存也算作投入资金后，收益率是否仍值得继续研究。

主方案是“向前采集，再回放”：从现在开始定时保存 LI.FI 的真实报价，积累成自己的历史数据库，然后严格按当时可见的数据模拟交易。LI.FI 提供当前报价和执行数据，但不是完整历史报价库，不能用今天的接口准确还原几个月前的 LI.FI 路径。

## 1. 第一版回测范围

为了先验证最核心的套利逻辑，第一版只做最简单的长期持币版本：

| 项目 | 第一版选择 |
|---|---|
| 资产 | WETH / USDC |
| 链 | 先选择 2 条 LI.FI 当前支持、WETH/USDC 流动性较好的链；链和代币地址写入配置，不写死在代码中 |
| 库存来源 | 自有 WETH + USDC |
| 永续合约对冲 | 暂不加入 |
| 借入 WETH | 暂不加入 |
| 真实交易 | 不发送，只模拟 |
| 补库存 | 模拟自然反向成交和 LI.FI 跨链补库存 |
| LI.FI 接入 | REST API；保存完整请求与原始响应 |

第一版不加入永续合约和借款，是为了先回答“价差本身能不能覆盖交易与补库存成本”。如果最简单的版本都没有稳定优势，加入杠杆或复杂对冲只会掩盖问题。

## 2. 为什么回测使用 API，而不是 SDK

回测采集器建议直接调用 LI.FI REST API：

- 可以完整保存 URL、参数、响应时间、HTTP 状态和原始 JSON；
- API 字段与数据库字段能一一对应；
- 不会因为 SDK 升级后默认行为变化而难以解释旧数据；
- 回测只读取报价，不需要 SDK 的钱包和执行封装。

以后编写真实交易程序时，可以重新评估是否使用 SDK；采集和回测仍应保留原始 API 数据。

## 3. 如何比较两条链

### 3.1 固定 WETH 数量

每次比较必须使用相同的 WETH 数量 `Q`。例如：

```text
链 A：买入 0.25 WETH，需要多少 USDC？
链 B：卖出 0.25 WETH，最少能收到多少 USDC？
```

不能简单地在两条链各使用 1,000 USDC，因为两边最终成交的 WETH 数量不同，会留下额外的价格风险。

### 3.2 买入侧报价

使用 LI.FI 的“指定最终收到数量”报价：

```text
GET /v1/quote/toAmount

fromChain = 链 A
toChain   = 链 A
fromToken = USDC 地址
toToken   = WETH 地址
toAmount  = Q
fromAddress = 固定的研究钱包地址
slippage = 允许的最大价格变化
```

记录为买到 `Q` WETH 预计需要的 USDC：

```text
buyRequiredUsdc = estimate.fromAmount
```

### 3.3 卖出侧报价

使用普通的“指定付出数量”报价：

```text
GET /v1/quote

fromChain = 链 B
toChain   = 链 B
fromToken = WETH 地址
toToken   = USDC 地址
fromAmount = Q
fromAddress = 固定的研究钱包地址
slippage = 允许的最大价格变化
```

使用最低到账量，而不是乐观的预计到账量：

```text
sellMinUsdc = estimate.toAmountMin
```

### 3.4 两个方向都计算

同一时刻需要计算：

```text
方向 1：链 A 买入，链 B 卖出
方向 2：链 B 买入，链 A 卖出
```

只有利润更高且库存足够的方向，才可能进入模拟交易。

## 4. 保守利润公式

```text
扣费前价差
= 卖出侧最低收到的 USDC
- 买入侧需要支付的 USDC

保守净利
= 扣费前价差
- 买入侧网络手续费
- 卖出侧网络手续费
- 没有包含在报价中的其他费用
- 预计补库存成本
- 买卖只有一笔成功的损失准备金
```

### 费用不能重复扣除

LI.FI 返回 `feeCosts` 和 `gasCosts`。处理规则：

- `gasCosts` 通常由钱包额外支付，要换算成美元后扣除；
- `feeCosts[].included = true` 表示费用已经反映在报价数量中，不能再扣一次；
- 只有没有包含在报价中的费用，才单独扣除；
- 保留原始费用数组，避免以后发现计算错误时无法重算。

第一版决策使用 `toAmountMin`。如果交易成功，模拟结果按最低到账量计算；如果价格已经差到低于最低到账量，应该模拟为交易失败并损失网络手续费，而不是假设能够以更差价格成交。

“预计补库存成本”和“买卖只有一笔成功的损失准备金”不能使用测试时间之后的数据。它们只能根据更早的训练数据估算，例如使用过去一段时间内每 1 WETH 补库存成本的 95 分位，以及不同失败情景的平均损失。完整回放结束后，再用实际模拟发生的补库存和失败损失替换准备金，计算最终真实结果。

## 5. 数据采集方案

### 5.1 两条采集流

必须同时采集两类数据：

| 采集流 | 用途 | 相对频率 |
|---|---|---|
| 同链买卖报价 | 判断链间价差能否交易 | 较高 |
| 跨链补库存报价 | 回放库存不足时的真实桥费、到账量和预计耗时 | 较低 |

跨链补库存报价至少覆盖：

```text
WETH：链 A -> 链 B、链 B -> 链 A
USDC：链 A -> 链 B、链 B -> 链 A
每个方向：多个补库存金额
```

如果只采集同链买卖报价，离线回测就无法知道历史时点的补库存成本。回测期间绝对不能临时调用今天的跨链报价，替代过去的报价。

### 5.2 采集频率

频率必须可配置，不能写死：

- 同链普通采集：每 15–60 秒一轮，根据实际 API 限额调整；
- 跨链补库存采集：可以更慢，例如每 5–15 分钟一轮；
- 接近盈利线时：可以短时间提高频率；
- 收到 HTTP 429 或服务异常时：降低频率，等待后重试；
- 记录所有漏采和错误，不能把“接口没返回”当成“没有套利机会”。

每轮的多条链、多种金额报价应并行请求，减少两边报价的时间差。LI.FI 需要等待外部 DEX、桥和链上模拟，响应时间会变化，因此必须记录请求开始和响应完成时间。

主数据集保持 LI.FI 的链上模拟开启，不使用 `skipSimulation=true`。如果要研究“关闭模拟能快多少”，应单独建立实验数据集，不能和主数据混在一起。

LI.FI 的等待策略会影响它能收集到多少第三方报价。所有采集任务必须保存当时使用的等待策略；同一个回测数据集应尽量保持策略一致。

具体频率要根据首批链数、金额档位、API 限额和漏采率确定。跨链报价间隔也要做敏感性测试；如果间隔太长，只能降低回测可信度，不能自动使用更早的报价。

### 5.3 交易金额

不要只测试一个金额。建议先使用一组相对 WETH 数量：

```text
0.05、0.10、0.25、0.50、1.00 WETH
```

这只是数据采集起点，不是建议交易金额。最终应根据策略总资金换算为“每笔使用可用库存的百分比”，并检查结果是否对多个金额都成立。

跨链补库存也应使用多个金额档位，因为桥费和到账损失未必随金额同比例变化。

### 5.4 必须保存的报价字段

| 分类 | 字段 |
|---|---|
| 时间 | 请求开始时间、响应时间、总耗时、UTC 日期 |
| 请求 | 链、代币地址、输入/目标数量、钱包地址、滑点、允许的交易所 |
| 金额 | `fromAmount`、`toAmount`、`toAmountMin`、代币小数位 |
| 费用 | 完整 `gasCosts`、`feeCosts`、美元金额、`included` |
| 路径 | `tool`、所有步骤、真正使用的交易所和资金池信息 |
| 交易 | `approvalAddress`、`transactionRequest` 是否存在 |
| 环境 | 两条链当时的区块号、原生代币价格、WETH 参考价格 |
| 错误 | HTTP 状态、LI.FI 错误码、错误信息、重试次数 |
| 原始数据 | 完整请求参数和完整响应 JSON |

### 5.5 推荐存储方式

第一版只使用 SQLite：

```text
lifi/data/
  quotes.sqlite
  reports/<run-id>/
```

每条记录同时保存常用索引字段和完整 `raw_json`，包括失败请求。这样既能快速按时间、链和方向查询，又能重新解析原始响应。数据库开启 WAL，并应定期备份；需要交换数据时再从 SQLite 导出 JSONL，不在采集时双写。

### 5.6 数据采集时间

最低目标：

- 先连续采集 2 周，用于验证采集器与回测程序；
- 再连续采集 6–8 周，用于初步判断策略；
- 数据应尽量覆盖平静期、网络拥堵期和价格快速波动期；
- 如果没有覆盖异常市场，结论只能写成“正常市场下可能成立”，不能写成“风险可控”。

## 6. 报价如何组成同一个决策时点

两条链的报价不可能在完全同一微秒返回。回测需要建立“报价组”：

```text
同一个 WETH 数量
+ 同一组链
+ 响应时间差小于允许值
= 一个可比较的报价组
```

第一版测试多个最大时间差：

```text
1 秒、3 秒、5 秒、10 秒
```

如果策略只有在允许使用 10 秒前的旧报价时才赚钱，说明机会可能无法真实执行。

做出交易决定时，只能使用当时已经返回的数据。未来的报价只能用于模拟交易提交后的价格变化，不能反过来帮助选择过去的交易，否则回测就是“偷看未来”。

## 7. 库存模型

### 7.1 初始库存

使用一个便于按比例换算的研究账户，例如总资产价值 100,000 美元。它只是计算单位，不是建议投入金额。

两条链可以先按以下方式平均分配：

```text
链 A：25% WETH + 25% USDC
链 B：25% WETH + 25% USDC
```

之后必须测试其他分配方式，例如 WETH/USDC 为 30/70、50/50、70/30，以及两条链不平均分配。

### 7.2 每条链保存的状态

```ts
interface InventoryState {
  chainId: number
  wethAvailable: bigint
  usdcAvailable: bigint
  wethReserved: bigint
  usdcReserved: bigint
  wethPending: bigint
  usdcPending: bigint
  gasTokenBalance: bigint
}
```

含义：

- `available`：现在可以用于新交易；
- `reserved`：已决定交易，正在等待模拟成交；
- `pending`：正在跨链或等待退款；
- 处理中和已预留的资金不能被下一次机会重复使用。

### 7.3 正常成交后的库存变化

假设链 A 买入、链 B 卖出 `Q` WETH：

```text
链 A：USDC 减少，WETH 增加 Q
链 B：WETH 减少 Q，USDC 增加
```

每次更新都使用模拟的真实成交数量，不能继续使用最初报价中的展示值。

### 7.4 如何计算整个策略值多少钱

交易利润以 USDC 记录，但全部 WETH 库存也必须按当时价格计算价值。估值价格应来自独立、可复查的数据源，例如可靠的链上价格预言机或多个深度较好的资金池中间价，不能只依赖 LI.FI 响应中的 `priceUSD`。

同时维护一个“不做任何套利”的对照账户：

```text
起点：和策略账户拥有完全相同的 WETH、USDC 和手续费余额
过程：不买、不卖、不跨链
终点：按同样的价格来源计算总资产价值
```

```text
套利带来的额外收益
= 策略账户总资产价值
- 不交易账户总资产价值
```

这样可以把“ETH 本身上涨或下跌”与“套利到底有没有增加收益”分开。若需要研究 USDC 脱锚，还应单独采集 USDC 的真实美元价格；第一版可以把它列为额外压力情景。

## 8. 成交模拟

### 8.1 不能假设看到报价就能成交

报价回测至少加入三段时间：

```text
获取两边报价 -> 做出决定 -> 交易被链确认
```

决策延迟、签名延迟和链上确认时间都应可配置。模拟成交时，应读取“决定之后”的下一组可用报价，判断原交易是否仍能达到 `toAmountMin`。

### 8.2 成功交易的成交价

保守版本：

- 买入成功：按买入报价要求的 USDC 加上额外成本；
- 卖出成功：按 `toAmountMin` 收到 USDC；
- 不模拟低于 `toAmountMin` 的成功成交；低于最低到账量时视为失败；
- 失败交易仍扣除网络手续费。

可另外运行中性版本：在 `toAmountMin` 与 `toAmount` 之间取一个随机成交量，但最终准入判断必须看保守版本。

### 8.3 买入和卖出只有一笔成功

必须分别模拟四种结果：

| 买入 | 卖出 | 结果 |
|---|---|---|
| 成功 | 成功 | 正常套利，更新两条链库存 |
| 失败 | 失败 | 不改变 WETH/USDC，只损失两边网络手续费 |
| 成功 | 失败 | WETH 变多；需要尽快补卖 |
| 失败 | 成功 | WETH 变少；需要尽快补买 |

处理步骤：

1. 在下一份可用报价中寻找补做失败交易的价格；
2. 计算补做时的价格变化、滑点和额外网络手续费；
3. 如果原链没有可用报价，尝试配置中的备用交易所或备用链；
4. 超过最大等待时间仍无法补做时，按当时 WETH 市价计算未处理风险；
5. 单独记录这类损失，不能混入正常交易费用。

在没有小额真实交易数据前，不要假装知道准确失败率。第一版使用多组情景：

```text
低失败情景：两边大部分时间成功
普通情景：偶尔只有一笔成功
压力情景：链拥堵或节点异常时连续失败
```

具体概率放在配置文件中，并在报告中完整展示。以后再用模拟交易和小额真实交易校准。

### 8.4 抢跑和竞争

`toAmountMin` 已经表示允许的最低到账量，不应在成功交易中随意再减一次滑点，否则容易重复计算。

抢跑和市场竞争主要按以下方式模拟：

- 成交机会被别人先用掉，交易失败并损失网络手续费；
- 为更快成交支付更高网络手续费；
- 报价在提交前已经过期；
- 分别测试公开提交和私有提交通道的失败率。

### 8.5 两级成交精度

第一版可以先做“报价级回放”：使用决定之后的下一组报价，近似判断原交易是否仍可达到最低到账量。它实现快，但只能说明策略值得不值得继续研究，不能证明原始交易一定能成交。

第二级应做“历史区块模拟”：

1. 保存原报价的 `transactionRequest`；
2. 使用能够读取历史状态的节点，在决定后的目标区块复制链上状态；
3. 给测试账户准备相同余额与授权；
4. 模拟原始交易调用，而不是重新获取一条新路径；
5. 记录是否成功、实际余额变化和消耗的网络手续费。

最终结论要分别标注：

```text
报价级结果：近似结果，适合筛选策略
历史区块模拟结果：更接近真实执行，适合决定是否进入实时模拟
```

如果两级结果差异很大，应以历史区块模拟为准，并查明是路径变化、价格变化、授权、余额还是节点状态造成。

## 9. 补库存模拟

### 9.1 先等待自然恢复

如果下一次机会方向相反，应优先用反向套利恢复库存，不应每完成一笔交易就立刻跨链。

### 9.2 库存上下限

第一版使用可配置的两级限制：

```text
提醒线：某资产低于目标库存的 30%
强制处理线：某资产低于目标库存的 15%
```

这些数值只是待测试起点。回测要同时测试 10%、15%、20%、30%、40% 等不同设置，寻找一段稳定范围，而不是挑一个历史收益最高的数值。

### 9.3 跨链补库存

达到强制处理线时：

1. 计算两条链的净缺口；
2. 合并多次交易产生的缺口，只跨链一次；
3. 获取当时的 LI.FI 跨链报价；
4. 扣除桥费、两条链网络手续费、滑点和资金占用成本；
5. 资产进入 `pending`，到达前不能用于新交易；
6. 按完成、只完成一部分、已退款和失败分别更新库存。

第一版历史数据不足时，桥接结果使用多组耗时和失败情景。之后可用小额桥接实验采集真实的完成时间、到账数量和状态分布。

离线回测中的“当时跨链报价”必须来自第 5 节提前保存的跨链报价采集流，并满足最大报价年龄限制；没有可用历史报价时，该次补库存应记为“无法执行”，不能调用当前 API 补数据。

### 9.4 对照组

必须同时运行：

- 完全不补库存；
- 每笔交易后立即补库存；
- 只有达到强制处理线才补库存；
- 只等待反向套利自然恢复。

这样才能知道收益到底来自价差，还是来自某个过于乐观的补库存假设。

## 10. 回测参数

所有参数放入配置文件，并写入每次结果目录：

```ts
interface BacktestConfig {
  chainIds: number[]
  wethAddresses: Record<number, string>
  usdcAddresses: Record<number, string>
  wethTradeSizes: string[]
  initialCapitalUsd: number
  initialInventoryWeights: Record<string, number>
  maxQuoteAgeMs: number
  decisionDelayMs: number
  confirmationDelayMs: Record<number, number>
  minProfitUsd: number
  minProfitBps: number
  maxTradeInventoryPct: number
  inventoryWarningPct: number
  inventoryHardLimitPct: number
  maxUnmatchedValueUsd: number
  maxUnmatchedDurationMs: number
  dailyFailedGasLimitUsd: number
  bridgePendingLimitPct: number
  randomSeed: number
}
```

金额计算不要使用 JavaScript `number` 处理链上最小单位。代币原始数量使用 `bigint`，美元与比例使用明确精度的十进制定点数，避免浮点误差制造假利润。

## 11. 防止回测结果过度乐观

| 常见错误 | 防范方法 |
|---|---|
| 用同一时刻最优买价和卖价，假设都能成交 | 加入报价响应时间、决策延迟和确认延迟 |
| 用 `toAmount` 当作必然到账 | 准入和保守结果使用 `toAmountMin` |
| 费用重复扣除或漏扣 | 检查 `feeCosts[].included`，费用分类记账 |
| 忽略失败交易的网络手续费 | 所有失败结果都扣除网络手续费 |
| 假设买卖永远一起成功 | 显式模拟四种成功/失败组合 |
| 资金跨链后立即可用 | 在实际或模拟完成时间前保持 `pending` |
| 忽略中间代币 | “只完成一部分”时按真实代币和真实价值入账 |
| 同一份库存同时执行多次机会 | 决策时先转入 `reserved`，确认后再更新 |
| 用今天的 LI.FI 路径还原历史 | 以持续保存的真实报价为主；历史链上数据只作补充 |
| 把连续出现的同一个价差重复算成很多机会 | 资金决定交易后立刻转为 `reserved`；确认前不能再次使用；同一机会设置冷却时间 |
| 不同采集等待策略混在一起 | 保存 LI.FI 等待策略，并分数据集比较 |
| 反复调参数直到历史盈利 | 按时间切分训练、验证和最终测试数据 |
| 只保留成功返回的 API 样本 | 同时保存超时、429、无路径和错误响应 |
| 只按成交金额计算收益率 | 按所有链上的 WETH、USDC、手续费余额和在途资金计算 |

## 12. 数据切分与参数选择

不能随机打乱时间。建议按时间顺序切分：

```text
前 60%：开发和初步调整参数
中间 20%：比较候选参数
最后 20%：最终测试，确认前不得查看结果
```

数据足够长后，再做滚动测试：使用前一段时间确定参数，在紧接着的下一段时间验证，然后向前移动。

参数选择的目标不是找到单个最高收益点，而是找到一段稳定区域。例如最低利润要求为 10、15、20 个基点时都能赚钱，比只有 13 个基点时盈利更可信。

## 13. 必须输出的报告

### 13.1 收益

- 扣费前价差收益；
- 两边网络手续费；
- LI.FI/DEX 其他费用；
- 买卖只有一笔成功造成的损失；
- 补库存成本；
- WETH 库存价格涨跌；
- 相比“相同 WETH 一直持有不动”多赚或少赚多少；
- 最终净收益和按全部投入资金计算的年化收益。样本不足一年时，年化值只用于比较，不能当作未来收益预测。

### 13.2 风险

- 最大资金回撤；
- 最差单笔损失；
- 连续亏损次数；
- 买卖只有一笔成功的次数、比例和损失分布；
- 最大未匹配 WETH 数量与持续时间；
- 每条链最大资金占比；
- 跨链在途资金的最大占比和最长时间；
- 完成、只完成一部分、退款和失败的比例。

### 13.3 执行质量

- 发现的机会数、实际可执行数和模拟成交数；
- 报价到模拟成交期间，利润减少了多少；
- 报价响应时间和两边报价时间差；
- 不同 WETH 数量下的净利润；
- 每条链、交易所和路径的收益与失败率；
- 因库存不足而错过的机会比例；
- 网络手续费和补库存成本占扣费前收益的比例。

### 13.4 图表

至少生成：

1. 策略总资产价值曲线；
2. 相对单纯持有 WETH 的累计多赚/少赚曲线；
3. 各链 WETH 与 USDC 库存曲线；
4. 扣费前价差与扣费后利润分布；
5. 不同交易金额的净利润曲线；
6. 买卖只有一笔成功的损失分布；
7. 补库存费用和在途时间分布；
8. 报价出现后，利润随等待时间衰减的曲线。

## 14. 压力测试

每组正常回测结果还要重复运行以下情景：

| 情景 | 改变什么 |
|---|---|
| 网络拥堵 | 网络手续费提高 2、5、10 倍 |
| 报价变旧 | 决策与确认延迟提高到正常值的 2、5 倍 |
| 流动性下降 | 可成交量减少，价格影响扩大 |
| 单链故障 | 一条链在 10 分钟、1 小时、6 小时内不能交易 |
| 节点/API 故障 | 连续漏掉报价或返回旧数据 |
| 买卖只成功一笔 | 失败概率提高，并模拟连续发生 |
| 桥接变慢 | 跨链耗时提高到正常值的 2、5、10 倍 |
| 桥接异常 | 提高只完成一部分、退款和失败比例 |
| 单向价差 | 很长时间只有同一个买卖方向，快速耗尽库存 |
| WETH 大幅波动 | 模拟价格快速上涨和下跌，观察未匹配资产损失 |

关键结论必须在多个相邻参数和压力情景下仍成立，不能只展示最好的一次运行。

## 15. 通过与停止条件

### 可以进入实时模拟交易

必须全部满足：

- 最终测试集使用 `toAmountMin` 后，扣除全部成本仍有正收益；
- 相比“相同 WETH 一直持有”，套利部分确实增加了收益；
- 至少三个相邻的交易金额和利润门槛都得到相近结论；
- 买卖只有一笔成功的最差损失没有突破预设风险预算；
- 补库存成本没有吞掉大部分扣费前收益；
- 任意一条链暂停时，策略不会被迫以无法接受的价格交易；
- 结果不是由单个异常日、单条链或单个交易所贡献；
- 原始数据缺失率、API 错误率和报价时间差在可接受范围内。

### 应停止或重新设计

出现任一项即停止：

- 只有使用乐观 `toAmount` 才盈利；
- 加入正常延迟后，利润大部分消失；
- 一次买卖不同时成功的损失能吞掉数周或数月收益；
- 补库存后长期净收益为负；
- 利润只存在于无法成交的小金额；
- 库存经常耗尽，大量机会无法执行；
- 最终测试集明显亏损；
- 参数轻微变化就从大赚变成大亏；
- 缺失或错误报价被错误地当成没有风险。

## 16. 实施顺序

### 阶段 A：报价采集器

完成内容：

- 读取链、代币和交易金额配置；
- 并行请求买入和卖出报价；
- 将完整请求、响应和错误写入 SQLite 的 `raw_json`；
- 处理超时、429、重试和断点恢复；
- 记录两条链区块号和响应时间。
- API Key 只从服务端环境变量读取，不能写入源码、日志或原始请求文件。

验收：连续运行 48 小时，不丢失已返回数据，重启后不会重复记录；备份可以正常恢复。

### 阶段 B：数据整理器

完成内容：

- 从 SQLite 的 `raw_json` 生成统一报价记录；
- 正确处理代币小数位和费用是否已包含；
- 组成同一时点的双链报价组；
- 检测地址、链和金额不一致。

验收：随机抽取至少 100 组报价，手工计算与程序结果一致。

### 阶段 C：无库存限制的机会扫描

完成内容：

- 先假设资金无限；
- 只检查价差、费用和延迟；
- 输出不同金额的机会数量与利润分布。

目的：快速判断市场是否存在足够多的候选机会。如果此阶段都没有正收益，不继续增加库存和桥接复杂度。

### 阶段 D：完整库存回测

完成内容：

- 加入每条链 WETH/USDC 库存；
- 预留和处理中资金不可重复使用；
- 加入买卖只有一笔成功；
- 加入自然恢复和跨链补库存；
- 计算整体资产价值与相对单纯持有的收益。

### 阶段 E：压力测试与最终测试集

完成内容：

- 运行所有压力情景；
- 固定参数；
- 最后才运行未查看的最终 20% 数据；
- 生成一份不可修改的结果目录和配置摘要。

### 阶段 F：实时模拟交易

完成内容：

- 使用实时 LI.FI 报价做决定；
- 不发送交易；
- 在未来区块检查假设交易是否还能成交；
- 每日比较实时模拟与历史回测的偏差。

只有实时模拟结果和回测接近，才值得另行设计小额真实交易方案。
