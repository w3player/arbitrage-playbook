# LayerZero 多链币价差套利项目计划

> 本文只做产品、数据、策略、合约与上线规划，不包含实现代码。  
> 项目必须依次经过只读扫描、历史验证、模拟交易、测试网、小额实盘五道门槛，任何阶段都不能直接跳到大额自动交易。

## 先给结论

这个项目不是简单比较两个页面上的币价，而是建立一条可审计的完整链路：

1. 找到真正属于同一全局供应体系的多链资产；
2. 验证每条跨链路径、合约权限和安全配置确实可用；
3. 比较相同数量资产在不同链上的可成交价格；
4. 扣除 DEX 滑点、Gas、LayerZero、失败恢复和补库存成本；
5. 只有保守净利润达标时才生成机会；
6. 使用多链预置库存并行成交，跨链主要负责事后补库存；
7. 所有交易先模拟、再受限执行、最后按链上回执核账。

第一阶段建议只研究 SIGN 和 DOS，覆盖 Ethereum、BNB Chain、Base。先支持标准 LayerZero V2 `OFT` 与 `OFTAdapter`，再扩展 Stargate 和自定义 OApp。

## 1. 项目目标与边界

### 1.1 目标

- 自动发现和维护 LayerZero 多链资产目录；
- 识别资产在不同链上的真实跨链架构；
- 持续采集相同资产、相同数量的链上可成交报价；
- 计算包含全部显性和隐性成本的保守净价差；
- 模拟多链预置库存套利、库存失衡和跨链补库存；
- 在满足安全门槛后，以受限合约执行真实交易；
- 保存从原始数据、决策、签名到链上回执的完整审计记录。

### 1.2 第一版不做

- 不追求所谓“跨链原子套利”；不同链无法天然原子成交；
- 不使用闪电贷作为第一版资金来源；
- 不自动交易未验证源码、代理实现不明或安全配置不清晰的资产；
- 不在发现价差后临时跨链再卖出作为主要模式；跨链延迟会使价差失效；
- 不把展示价格、池中间价或第三方价格页面当作可成交价格；
- 不把合约管理员权限、DVN 配置和暂停状态排除在风险模型之外；
- 不在没有模拟、限额、暂停和恢复流程时接入真实私钥。

## 2. 总体架构

项目分成六层，每层只依赖下层已经确认的数据：

| 层级 | 职责 | 主要输出 |
|---|---|---|
| 资产发现层 | 收集候选 LayerZero 多链资产 | 候选资产与来源证据 |
| 链上验证层 | 读取合约、peers、Endpoint、权限和安全配置 | 已验证资产拓扑 |
| 市场数据层 | 采集 DEX/CEX、Gas、跨链和流动性数据 | 标准化可成交报价 |
| 机会决策层 | 计算净价差、容量、置信度和风险 | 可执行机会或拒绝原因 |
| 执行与恢复层 | 模拟、下单、跨链补库存和失败恢复 | 交易、回执与库存变化 |
| 审计监控层 | 对账、告警、绩效和配置变更记录 | 报告、指标和审计日志 |

任何资产进入价格扫描前，必须先完成链上验证；任何机会进入执行前，必须先通过库存、成本、模拟和风险检查。

## 3. 多链资产扫描计划

### 3.1 候选资产来源

扫描器不能只依赖 LayerZero 官方 OFT 列表，因为 SIGN、DOS 这类资产可能没有登记在公共元数据 API。候选来源按优先级组合：

1. LayerZero 官方 OFT 元数据与链部署目录；
2. Stargate V2 官方资产元数据；
3. LayerZero Scan 的消息、OApp 与合约关系；
4. 各项目官方 Bridge、文档和 Token 地址；
5. 区块浏览器的已验证合约源码、ABI 和构造参数；
6. Endpoint 相关事件，包括 peer、delegate 和配置变更；
7. 已知工厂、部署者和相同字节码生成的候选合约；
8. 人工提交的 Token 地址。

每条候选记录必须保留来源 URL、发现时间、链、地址和来源可信级别。搜索结果或代币符号只能作为候选，不能直接作为事实。

### 3.2 需要识别的资产类型

| 类型 | 识别重点 | 典型资金变化 |
|---|---|---|
| LayerZero V2 Direct OFT | Token 本身包含 `send`、`quoteSend`、`peers` | 源链销毁，目标链铸造 |
| OFTAdapter | Token 与桥合约分离，Adapter 绑定底层 Token | 源链锁定，目标链铸造；返回时相反 |
| Mint/Burn Adapter | Adapter 获得 Token 铸造与销毁权限 | 两侧按权限销毁和铸造 |
| Stargate Pool | 底层 Token、Pool、Credit 与 TokenMessaging | 流动性池锁定和释放 |
| Stargate OFT/Hydra | Stargate Pool 支撑的远端资产 | 远端销毁和铸造 |
| Stargate Native | ETH 等原生资产的 Stargate 路径 | 原生资产池记账 |
| LayerZero V1 OFT | 旧 Endpoint、trustedRemote、sendFrom | V1 消息与供应调整 |
| 自定义 OApp 桥 | 只有部分 OFT 接口或完全自定义逻辑 | 由项目合约定义 |

第一版仅自动批准 Direct OFT 和标准 OFTAdapter。其他类型先扫描、分类和报告，不进入自动交易白名单。

### 3.3 每个部署必须采集的字段

#### 身份信息

- 项目名、Token 名称、符号和小数位；
- chainId、LayerZero Endpoint ID、网络名称；
- Token 地址、OFT/Adapter 地址、代理地址和实现地址；
- 合约名称、源码验证状态、编译器和字节码哈希；
- 创建者、部署交易、创建区块和部署时间。

#### OFT 与跨链信息

- Endpoint 地址与版本；
- `token`、`approvalRequired`、`oftVersion` 和 shared decimals；
- 所有非零 `peers`，以及 peer 对应的链和合约；
- 每个方向是否形成双向可信关系；
- enforced options、send/receive library 与超时配置；
- 支持的目标链、最小数量、精度损失和 dust 处理；
- LayerZero 原生费、LZ Token 费和退款地址规则；
- 最近成功发送、接收和失败消息。

#### 权限和安全信息

- owner、delegate、proxy admin、upgrader 和 pauser；
- 是否可暂停、冻结、拉黑、增发、销毁或救援资产；
- DVN 组合、确认数、执行器和消息库；
- 安全配置是否使用默认值，最近是否发生变更；
- Adapter 锁仓余额与远端流通供应是否能够对账；
- 是否存在速率限制、单笔上限或每日额度；
- 审计信息、漏洞公告和异常交易标记。

### 3.4 拓扑验证规则

一个资产被认定为可研究的多链币，需要同时满足：

1. 至少存在两条链的部署；
2. 两端 Endpoint 均为已知 LayerZero Endpoint；
3. A 链 peer 指向 B 链合约，B 链 peer 也指回 A 链；
4. 地址编码、Endpoint ID 和链映射正确；
5. `quoteSend` 可返回报价，静态模拟不会立即失败；
6. 最近存在成功的发送与接收，或项目处于已确认的新部署阶段；
7. Token 名称相同不是充分条件，必须证明供应或抵押关系；
8. Adapter 必须确认绑定的底层 Token；
9. 代理必须解析到实现合约，不能只读取代理 ABI；
10. Similar Match 源码必须降级可信度，关键结论需要链上调用或字节码验证补强。

### 3.5 资产可信等级

| 等级 | 条件 | 用途 |
|---|---|---|
| A | 官方地址、Exact Match、双向 peer、近期成功消息、安全配置完整 | 可进入模拟和小额实盘候选 |
| B | 核心链上关系已确认，但元数据、审计或部分安全配置缺失 | 只做价格观察和模拟 |
| C | Similar Match、单向 peer、代理不明或长期无消息 | 只保留研究记录 |
| D | 地址冲突、Token 关系不成立、安全异常或疑似假币 | 禁止报价和执行 |

### 3.6 增量扫描与变更监控

- 首次执行全量扫描；
- 后续按区块增量读取新增部署和事件；
- 定期重新读取 owner、peer、delegate、pause 和安全配置；
- 配置变化时生成新版本，不能覆盖历史状态；
- peer 被移除、合约暂停、实现升级或 DVN 降级时，立即冻结相关机会；
- 资产目录中的每个结论都要关联原始 RPC 响应或浏览器证据。

### 3.7 扫描阶段输出

- 已验证资产清单；
- 每个资产的多链节点和跨链边；
- 类型：Direct OFT、Adapter、Stargate 或自定义；
- 可用、暂停、单向、失联和待确认状态；
- 可信等级与拒绝原因；
- 适合人阅读的资产报告；
- 供价格检查器读取的机器化白名单。

## 4. 价格与价差检查计划

### 4.1 交易模型优先级

| 模型 | 描述 | 优先级 |
|---|---|---|
| 多链预置库存 | 低价链用稳定币买入，高价链同时卖出已有 Token，事后补库存 | 第一优先 |
| 单边成交后恢复 | 一边成功、一边失败后立即反向平仓或对冲 | 必须支持 |
| 发现后先跨链再卖 | 买入后跨链，到账后卖出 | 只做研究，不作为第一版实盘 |
| CEX 与链上套利 | CEX 买卖配合链上库存 | 后续扩展 |
| 跨链 Compose | 到账后自动调用 DEX | 后续实验，不能视为跨链原子性 |

选择预置库存，是因为买卖可以近似同时提交，跨链只承担补库存职责，不让套利机会暴露在数分钟的桥接延迟中。

### 4.2 市场数据来源

- 各链主流 DEX 的直接 Quoter 或 Router 静态报价；
- DEX 聚合器的可执行报价和 calldata；
- 必要时加入 CEX 最优买卖盘及指定深度；
- 各链 Gas Price、Base Fee、优先费和原生币美元价；
- LayerZero `quoteSend` 的实时消息费用；
- Stargate 的协议费用、池深度和 Credit 状态；
- 独立参考价格，用于异常检测和资产估值；
- 池储备、tick、手续费档位、交易税和 Token 行为。

所有报价必须保存原始请求和响应，不能只保存最终价格。

### 4.3 报价比较原则

1. 两条链比较完全相同的 Token 数量；
2. 买入侧优先使用“指定最终收到数量”的报价；
3. 卖出侧使用“指定付出数量”的最低到账量；
4. 同时计算 A 买 B 卖和 B 买 A 卖；
5. 记录两边请求开始、响应、区块和最大时间差；
6. 报价超时、跨区块过多或池状态已变化时立即失效；
7. 不同小数位先转换为统一共享精度，避免 dust 被误当利润；
8. 对多个数量档位报价，形成“利润—规模”曲线；
9. 最优报价必须能够生成可模拟的交易请求；
10. 报价来源与执行 Router 必须在白名单中。

### 4.4 第一批数量档位

数量应按资产价值和池深度动态调整。初始研究可以采用约 100、500、1,000、2,500、5,000 美元五档等值规模，然后为每个资产生成实际 Token 数量。

每档都要独立报价，不能用小额价格线性推算大额成交。只有连续多个档位都显示正净利，才说明机会具有真实容量。

### 4.5 完整成本模型

保守净利润由以下部分组成：

| 项目 | 处理方式 |
|---|---|
| 高价链卖出收入 | 使用最低到账量，不使用展示金额 |
| 低价链买入成本 | 使用完成固定 Token 数量所需的最大稳定币金额 |
| 两侧 DEX 费用 | 已包含的费用不得重复扣除 |
| 价格影响和滑点 | 使用实际数量的 Router 报价与最小到账 |
| 两侧 Gas | 按拥堵上行情景估算，并换算成美元 |
| 授权成本 | 首次授权或重新授权时计入 |
| 跨链补库存成本 | 使用历史和当前可执行桥接报价估算 |
| LayerZero/Stargate 费用 | 以 `quoteSend` 或协议实时报价为准 |
| 失败准备金 | 根据单边失败、回滚和紧急平仓历史分位数计提 |
| 库存占用成本 | 计入多链闲置资金与补库存等待时间 |
| 对冲成本 | 如果使用永续合约，计入手续费、资金费和基差 |

核心决策值包括：毛价差、直接执行净利、计入补库存后的净利、最坏情景净损失、资金收益率和年化机会频率。系统不得只展示毛价差。

### 4.6 机会准入条件

一次机会必须同时满足：

- 资产可信等级达到策略要求；
- 合约未暂停、peer 完整、安全配置没有新变更；
- 两侧报价在最大时间差内；
- 两边池深度和预期价格影响合格；
- 两链库存和 Gas 余额充足；
- 保守净利润同时超过美元门槛和基点门槛；
- 最坏情景亏损低于单笔风险限额；
- 交易后库存不会跌破硬下限；
- 模拟执行成功且状态没有过期；
- 没有同一资产的进行中冲突交易；
- 全局、单链、单资产和单 Router 限额都未触发。

不满足时必须记录明确拒绝原因，便于统计“机会为什么消失”。

### 4.7 去重和冷却

- 同一资产、方向、数量和报价窗口生成稳定机会 ID；
- 状态未显著变化时不重复下单；
- 每个资产和方向设置冷却期；
- 前一笔尚未完成核账时冻结相同库存；
- 连续失败、报价偏差过大或 Gas 激增时自动延长冷却；
- 机会阈值使用进入线与退出线，防止在边界反复触发。

### 4.8 价差数据与回测

必须向前保存真实可执行报价，再按当时可见数据回放。至少保存：

- 两侧原始报价与 calldata；
- Token、链、Router、池和数量；
- 请求与响应时间、区块号和延迟；
- 预计金额、最低到账、Gas 和所有费用；
- 独立参考价格与流动性；
- 当时资产拓扑和安全配置版本；
- 机会判断、阈值、拒绝原因和策略版本；
- 未来实际区块状态，用于模拟执行结果，但不能用于过去决策。

回测必须与“不交易、原样持有库存”的基准比较，并单独统计毛利润、执行损失、补库存成本和闲置资金成本。

## 5. 库存与资金计划

### 5.1 初始库存

每条目标链同时预置套利 Token、稳定币和 Gas Token。初始分配不是固定答案，至少测试：

- 各链等权；
- 按历史成交量分配；
- 按历史机会方向分配；
- Token 与稳定币 30/70、50/50、70/30；
- 极端单向价差下的库存耗尽速度。

### 5.2 库存状态

每条链、每个资产区分：

- 可用余额；
- 已为机会预留余额；
- 已提交但未确认余额；
- 正在跨链余额；
- 等待退款或恢复余额；
- 最低安全库存；
- 目标库存；
- Gas 安全余额。

任何资金只能处于一个状态，不能被两个机会重复占用。

### 5.3 补库存策略

优先级如下：

1. 等待自然反向套利恢复库存；
2. 当库存触及软阈值时计算主动补库存成本；
3. 选择已验证的 OFT、Adapter 或 Stargate 路径；
4. 库存触及硬阈值时停止消耗该方向；
5. 只有补库存成本低于未来预期收益时才执行；
6. 跨链中的资产不能计入可用库存；
7. 超时未到账必须进入恢复流程，而不是再次重复发送。

补库存本身是独立交易，需要单独保存报价、消息 GUID、源链交易、目标链交付、到账数量、耗时和失败原因。

## 6. 合约执行计划

### 6.1 为什么仍然需要链下协调器

跨链套利无法由一个 EVM 交易原子完成。执行系统应采用“链下协调器 + 每链受限执行合约”：

- 链下协调器负责行情、机会、库存、并行发送、状态机和恢复；
- 每链执行合约只负责受限授权、DEX 交换、OFT/Adapter 发送和资产保管；
- 合约不能自行相信链下展示价格，必须执行最小到账、截止时间和白名单检查；
- 两条链的交易可能一成一败，协调器必须显式处理该状态。

### 6.2 上线阶段

| 阶段 | 执行方式 | 是否使用真实资金 |
|---|---|---|
| E0 | 只生成机会和模拟结果 | 否 |
| E1 | 生成待签交易，由人检查但不广播 | 否 |
| E2 | 测试网执行合约和 LayerZero 路径 | 测试币 |
| E3 | 主网影子模式，生成交易但不签名 | 否 |
| E4 | 主网人工确认、小额白名单执行 | 是，严格限额 |
| E5 | 自动执行，但保留全局熔断与逐级限额 | 是，逐步放大 |

任何阶段升级都需要独立验收，不因代码完成自动升级。

### 6.3 每链执行合约职责

- 仅接受授权执行者调用；
- 维护允许的 Token、DEX Router、OFT/Adapter 和目标链白名单；
- 限制单笔、每日、单 Token 和单 Router 最大金额；
- 执行 Token 授权，优先使用精确额度或使用后归零；
- 调用白名单 DEX 完成买入或卖出；
- 强制最小到账、最大支付、截止时间和接收地址；
- 调用 OFT/Adapter 的报价与发送接口；
- 设置 LayerZero 最小到账、目标链、接收人、options 和退款地址；
- 记录机会 ID、输入、输出和桥接 GUID；
- 提供暂停、撤销授权和受控救援能力；
- 防重入、防重复机会、防错误原生币退款；
- 不允许任意目标合约和任意 calldata；
- 升级能力如非必要应避免；如使用代理，升级必须多签和延迟生效。

### 6.4 权限模型

至少区分：

| 角色 | 权限 |
|---|---|
| 策略执行者 | 在白名单与限额内执行交易，不能改配置或提走资金 |
| 风控暂停者 | 只能暂停，不能恢复或转移资金 |
| 配置管理员 | 修改白名单和限额，必须多签并有延迟 |
| 资金救援者 | 仅在暂停状态下按严格流程救援资产 |
| 升级管理员 | 如存在升级，仅负责实现升级，不参与日常交易 |

私钥不得出现在配置文件、数据库或日志。自动执行账户只保留满足限额的热资金，长期资金由独立多签管理。

### 6.5 交易执行状态机

一次套利按以下状态推进：

1. 机会已发现；
2. 报价已锁定并重新验证；
3. 两链库存已预留；
4. 两侧交易已静态模拟；
5. Nonce、Gas、截止时间和限额已确认；
6. 两侧交易近似同时提交；
7. 分别等待源链回执；
8. 根据双成、单成、双败进入对应分支；
9. 按实际余额和事件核账；
10. 释放未使用库存；
11. 必要时生成恢复或补库存任务；
12. 交易完成并写入不可变审计记录。

状态只能按允许方向转换。重启后必须从链上事实恢复，不能仅依赖内存状态。

### 6.6 四种成交结果

| 结果 | 处理 |
|---|---|
| 买卖都成功 | 记录实际净利，更新两链库存，评估补库存 |
| 买入成功、卖出失败 | 冻结新增 Token，重新报价后卖出、对冲或保留，执行损失限额 |
| 买入失败、卖出成功 | 形成 Token 空缺，重新买回、对冲或暂停该资产 |
| 买卖都失败 | 只记录 Gas 和失败原因，检查是否触发冷却或熔断 |

恢复操作也必须经过报价、模拟、限额和审计，不能为了“救单”绕过风控。

### 6.7 OFT/Adapter 跨链执行

跨链前必须确认：

- 当前 peer 没有变化；
- 目标链接收合约和地址编码正确；
- `quoteSend` 费用仍在上限内；
- Adapter 已获得正确授权；
- `amountLD`、`minAmountLD` 和共享精度正确；
- options 只包含预期执行参数；
- refund address 由策略控制；
- 目标链有足够交付能力；
- 消息和接收合约均未暂停；
- 当前路径没有积压或异常失败率。

第一版不使用 Compose 自动卖出。先确保资产安全到账，再由目标链独立交易，避免把桥接、消息执行和 DEX 失败耦合成难以恢复的流程。

### 6.8 交易前模拟

每笔真实交易都要执行：

- 最新区块静态调用；
- 余额、授权、Nonce 和 Gas 检查；
- Router 与合约白名单检查；
- 预期事件和余额变化检查；
- 最小到账和最大支付检查；
- 低 Gas、价格变化、授权不足和合约暂停情景检查；
- 必要时在最新主网分叉上完整回放。

模拟成功不是盈利保证，但模拟失败必须禁止广播。

### 6.9 MEV 与交易提交

- 买卖设置短截止时间；
- 最小到账不能因追求成功率而无限放宽；
- 对容易被夹击的交易评估私有交易通道；
- 监控交易在 mempool 中的等待时间；
- Nonce 管理由每条链独立串行化；
- 不盲目替换交易，替换前重新检查机会是否仍成立；
- 发生重组时等待策略定义的最终确认数再核账。

## 7. 风控与安全计划

### 7.1 风险限额

- 单笔最大名义金额；
- 单资产最大敞口；
- 单链最大资金占比；
- 单 Router、单池和单桥最大暴露；
- 每小时、每日最大交易次数；
- 每日最大已实现亏损；
- 最大未确认交易数；
- 最大跨链在途金额；
- 最大单边裸露时间；
- 最低 Gas 余额和最低可用库存。

### 7.2 自动熔断条件

- owner、peer、实现、DVN 或消息库发生未批准变化；
- Token 或跨链合约暂停；
- 报价源与独立价格偏差超过阈值；
- 连续模拟失败或连续单边成交；
- 实际到账持续低于预估；
- RPC、Indexer 或价格源大面积失联；
- LayerZero 消息长时间未交付；
- 库存、数据库和链上余额无法对账；
- 当日亏损或 Gas 消耗达到上限；
- 发现合约漏洞、攻击或项目方紧急公告。

熔断后只允许查询、对账和预定义救援操作，不允许继续开新仓。

### 7.3 Token 风险检查

- 转账税、动态手续费或反射机制；
- 黑名单、白名单、冻结和区域限制；
- 最大交易、最大钱包和交易冷却；
- 可增发、可销毁和供应上限；
- 代理升级和管理员权限；
- ERC-20 非标准返回值；
- rebasing、fee-on-transfer 和 decimals 异常；
- 假 Token、同名 Token 和不同供应体系；
- 流动性可撤出和池创建者集中风险。

不兼容标准 Router 或无法可靠预估到账的 Token，第一版直接禁止自动交易。

## 8. 数据模型与审计

建议至少包含以下逻辑数据集：

| 数据集 | 内容 |
|---|---|
| assets | 项目、符号、全局资产身份和可信等级 |
| deployments | 每链 Token、OFT、Adapter、实现和权限 |
| pathways | peer、Endpoint、方向、安全配置和可用状态 |
| venues | DEX、Router、池、费率和白名单状态 |
| raw_quotes | 原始请求、响应、时间、区块和错误 |
| normalized_quotes | 标准数量、最低到账、Gas 和有效期 |
| opportunities | 毛价差、净利、容量、风险和拒绝原因 |
| inventory | 可用、预留、在途、目标和安全库存 |
| executions | 状态机、策略版本、模拟和签名关联 |
| transactions | 链、Nonce、哈希、回执、事件和实际余额变化 |
| rebalances | 跨链 GUID、来源、目标、到账、耗时和恢复 |
| config_versions | 白名单、阈值、权限和策略配置历史 |
| incidents | 熔断、异常、处理过程和复盘结论 |

所有金额使用整数最小单位保存，同时保留 decimals；所有时间使用 UTC；所有决策关联配置版本和代码版本。日志不得包含私钥、签名原文或敏感 RPC 凭证。

## 9. 监控与报告

### 9.1 实时指标

- 候选资产数、已验证资产数和各可信等级数量；
- peer、权限和安全配置变更；
- 各链报价成功率、延迟和陈旧率；
- 机会数、被拒绝数和主要拒绝原因；
- 预估净利与实际净利偏差；
- 成交成功率、单边失败率和恢复耗时；
- 每链每资产库存、在途资产和 Gas 余额；
- LayerZero 消息交付时间与失败率；
- 累计利润、Gas、滑点、补库存和失败损失；
- 策略收益相对不交易基准的超额收益。

### 9.2 告警优先级

- P0：疑似资产损失、未授权配置变更、错误目标链、无法暂停；
- P1：单边成交未恢复、跨链超时、余额无法对账、日亏损超限；
- P2：报价源失联、库存触及硬阈值、模拟连续失败；
- P3：新资产候选、普通配置漂移、采集延迟上升。

### 9.3 定期报告

- 每日机会与执行摘要；
- 每周资产拓扑和配置变化；
- 每周策略收益、失败、补库存与资金利用率；
- 每月风险限额、权限、白名单与事故复查；
- 每次版本升级前后的回测和影子运行对比。

## 10. 测试计划

### 10.1 扫描测试

- Direct OFT、Adapter、Stargate 和自定义合约样本；
- Exact Match、Similar Match、代理和未验证源码；
- 单向 peer、错误 Endpoint、错误地址编码和被移除 peer；
- pause、owner、delegate 和实现升级；
- 不同 decimals 与 shared decimals；
- 官方元数据缺失但链上关系真实的 SIGN、DOS 类案例。

### 10.2 价格与策略测试

- 不同金额档位和不同池深度；
- 报价延迟、旧报价、区块跨越和 RPC 延迟；
- Gas 2、5、10 倍；
- 滑点扩大、流动性骤降和 Token 价格快速波动；
- 长期单向价差导致库存耗尽；
- 桥接费用上涨、消息延迟和补库存失败；
- 毛价差为正但真实净利为负；
- 报价重复、乱序和缺失。

### 10.3 合约测试

- 白名单、角色、暂停和限额；
- 正确授权、撤销授权和救援；
- 最小到账、最大支付和截止时间；
- 恶意 Router、任意 calldata、重入和重复机会；
- fee-on-transfer、无返回值和异常 decimals Token；
- OFT、Adapter、错误 peer、错误目标链和退款；
- 主网分叉上的真实 Router 和 LayerZero 合约；
- 买卖双成、单成、双败、重组和交易替换；
- 重启后的状态恢复与链上对账。

### 10.4 上线前压力测试

- 连续运行至少两周无人工修复；
- RPC 与报价源随机失败；
- 数据库短暂不可用和进程重启；
- 多机会并发和 Nonce 冲突；
- 熔断、暂停、恢复和资金救援演练；
- 消息长期卡住时不重复跨链；
- 极端行情下仍遵守单笔与日亏损限额。

## 11. 分阶段交付计划

### 阶段 P0：研究定义和样本

交付：资产分类规则、链与资产配置、SIGN/DOS 人工核验基准、风险字段清单。

验收：团队能够对同一地址给出一致的类型、Token/Adapter 关系和跨链方向判断。

### 阶段 P1：只读资产扫描

交付：候选采集、合约识别、部署记录、可信等级和人工报告。

验收：SIGN、DOS 的已知结论全部识别正确；假币和单向 peer 不进入白名单。

### 阶段 P2：跨链拓扑与安全验证

交付：peer 图、Endpoint、Adapter 绑定、安全配置、权限和变更监控。

验收：每条可用边都能提供双向链上证据；配置变化能够自动冻结资产。

### 阶段 P3：市场数据与价差检查

交付：多金额可执行报价、Gas、桥费、流动性和净价差报告。

验收：所有机会都可还原计算；同一输入重复计算结果一致；毛价差和净价差明确分离。

### 阶段 P4：历史回放与纸面交易

交付：库存状态机、失败模型、补库存模拟、基准账户和压力测试。

验收：没有偷看未来；单边失败和长期库存耗尽被正确计入；策略在保守情景仍有研究价值。

### 阶段 P5：测试网执行合约

交付：受限执行合约、权限、暂停、模拟、OFT/Adapter 跨链和恢复流程。

验收：安全测试通过；错误目标链、恶意 Router、超限和重复执行全部被拒绝。

### 阶段 P6：主网影子运行

交付：真实主网数据下的交易生成、模拟、预期回执和人工对照，不签名。

验收：连续两周运行稳定；预估成交与链上可成交状态偏差在阈值内；无错误机会进入待执行队列。

### 阶段 P7：小额人工确认实盘

交付：小额白名单资产交易、实时对账、告警、熔断和事故手册。

验收：完成预定笔数且无资金异常；实际净利、失败率和恢复成本符合模拟区间。

### 阶段 P8：受限自动执行

交付：自动签名与广播、分层限额、独立暂停者和多签配置管理。

验收：经过独立安全审查；热钱包限额、日亏损熔断和救援演练全部通过。

## 12. 每阶段禁止越过的门槛

| 从 | 到 | 必须满足 |
|---|---|---|
| 扫描 | 价差检查 | 资产拓扑和安全配置已验证 |
| 价差检查 | 模拟交易 | 报价可执行、成本完整、数据可回放 |
| 模拟交易 | 测试网 | 状态机与失败恢复通过压力测试 |
| 测试网 | 主网影子 | 合约安全测试与权限审查通过 |
| 主网影子 | 小额实盘 | 连续稳定运行、无错误待签交易 |
| 小额实盘 | 自动执行 | 实际结果符合模型，独立审查和熔断完成 |

## 13. 第一版建议配置

| 项目 | 建议 |
|---|---|
| 样本资产 | SIGN、DOS |

## 14. 开工顺序

1. 固化 SIGN、DOS 的人工基准资料；
2. 定义资产、部署、peer、报价、机会和库存字段；
3. 完成只读扫描与可信等级；
4. 完成 Direct OFT 和 OFTAdapter 拓扑验证；
5. 接入 BNB Chain、Base、Ethereum 的报价与 Gas 数据；
6. 建立固定数量、双方向净价差计算；
7. 持续采集至少两周，完成第一轮历史回放；
8. 加入库存、补库存和单边失败模拟；
9. 只有策略通过保守压力测试后，才设计并实现执行合约；
10. 按测试网、影子、小额人工、受限自动的顺序推进。

- 第一批 DEX 和报价聚合器；
